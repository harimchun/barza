기준: 현재 코드(`index.html`, `js/*.js`, `css/style.css`), 라이브 페이지(harimchun.github.io/barza), 팀 스프레드시트(경기 시트 31개 + 대시보드), Firebase 실데이터

## 1. 현재 상태 진단

### 1-1. 데이터 (가장 큰 문제)

| 항목 | 스프레드시트 | 앱(Firebase) |
|---|---|---|
| 경기 기록 | 31경기 (2026.1.3 ~ 10.17) | 3경기 (2.21, 3.14, 3.21) |
| 선수 선호 포지션 | 있음 (예: 주열 `RB, GK`, 재훈 `CAM, LDM`) | 없음 |
| 교체(In/Out) 기록 | 쿼터별 In/Out 열 | 포지션별 교체 선수 1명만 |
| 실 참여 쿼터 (교체 = 0.5) | 수식으로 계산·저장 | 화면 계산만 하고 저장 안 됨 (`squad_plan`은 true/false) |
| 쿼터 수 | 4쿼터 기본, 2.5시간 경기는 5쿼터 (6.13 신사중) | 4쿼터 고정 |
| 쿼터당 출전 인원 | 10~11명 (경기마다 다름) | 11명 고정 (목표 = 44/N) |
| 이름 별칭 | 수식에서 처리 (변정민=정민, 이해근=해근) | 없음 → 같은 사람이 두 명으로 집계될 수 있음 |
| 경기장 목록 | — | 기기별 localStorage (팀 공유 안 됨) |

결론: 지금은 시트가 진짜 원본이고 앱은 거의 비어 있다. 앱을 실제로 쓰려면 **시트 데이터를 한 번에 가져오는 이관 작업**이 먼저다.

### 1-2. DB 연동 구조의 약점

- `/matches.json` 전체 배열을 통째로 PUT → 두 사람이 동시에 편집하면 늦게 저장한 쪽이 상대 저장을 덮어씀. 자동저장(2분)이 켜져 있어 위험이 더 크다.
- 경기 ID가 `날짜_장소_상대팀` 문자열이라 셋 중 하나만 바꿔도 다른 경기로 저장(중복 발생).
- 로스터가 `{이름: 'Member'|'Guest'}`뿐이라 포지션·등번호·별칭·활동 여부를 넣을 자리가 없음.
- 게스트 추가 시 로스터 저장 실패를 조용히 무시(`.catch(() => {})`).
- 시즌 스탯의 CSV 업로드는 새로고침하면 사라지는 임시 기능.

### 1-3. 쿼터 보장 로직 — 시트 수식 정리 (앱에 그대로 옮길 규칙)

경기 시트 Q~X열, 대시보드 수식을 읽어 정리한 규칙:

```
참여(R)          = O / X  (당일 참석 여부)
쿼터별 출전(S~V)  = 해당 쿼터 보드(교체 In/Out 열 포함)에 이름이 있으면 O
참여횟수(W)       = 출전 쿼터 수
실 참여횟수(X)    = W − (In/Out 열에 등장한 횟수) / 2     ← 교체로 들어오거나 나간 쿼터는 0.5
참여인원          = R열의 O 개수
쿼터별 인원       = 쿼터 보드별 이름 수 (10 또는 11)
예상 평균쿼터     = (쿼터당 출전 인원 × 쿼터 수) / 참여인원    ← 4쿼터 11명이면 44/N, 5쿼터면 55/N
실제 평균쿼터     = 실 참여횟수 > 0 인 선수들의 평균
```

대시보드(시즌):

```
경기별: 참/불참(쿼터>0), 쿼터(= 실 참여횟수), 골, 어시
선수 누적: 참여횟수(경기 수), 총 쿼터(실 참여 합), 골, 어시, 공격포인트
팀: 승/무/패, 승률, 총 참석인원, 평균쿼터, 1~4쿼터별 득점/실점 합계
```

앱의 `getParticipation()`은 0.5 규칙을 화면에서는 계산하지만, 저장 레코드에는 반영되지 않고 쿼터 수·출전 인원이 고정이라 시트와 결과가 달라진다.

### 1-4. 디자인/UX (라이브 페이지 확인 결과)

- 피치 위 포지션 카드 안에 `<select>` 두 개가 들어가 있어 모바일에서 너무 작고, 드래그와 선택이 섞여 조작이 헷갈림.
- "전체 쿼터 포메이션 개요" 미니맵 4개가 화면을 크게 차지하지만 이름 2글자만 보여 정보량이 적음.
- 참석자 체크리스트가 48명 2열로 길게 늘어져, 모바일에서는 포메이션까지 스크롤이 매우 김.
- 각 선수가 "지금까지 몇 쿼터 / 목표 몇 쿼터"인지 배치 중에 바로 보이지 않음(벤치 칩에만 작게 표시).
- 이모지 라벨이 많고 카드 테두리·그림자가 무거워 위계가 흐릿함. 블라우그라나 색 테마 자체는 유지할 만함.
- 기록 탭 진입 시 페이드인이 느려 처음 2~3초 화면이 거의 안 보임.

## 2. 목표 상태

1. 앱이 시트를 완전히 대체한다: 과거 31경기 + 선호 포지션 + 별칭이 DB에 있고, 시즌 통계가 대시보드와 같은 숫자를 낸다.
2. 쿼터 보장 계산이 시트 수식과 1:1로 같다(교체 0.5, 가변 쿼터 수·출전 인원, 목표 쿼터).
3. 참석자만 체크하면 선호 포지션과 쿼터 균형을 반영한 **자동 초안**이 나오고, 손으로 다듬는다.
4. 경기장에서 폰으로 쓰기 편한 화면.

## 3. 단계별 계획

### Phase 0 — 데이터 모델 정리 + 시트 이관 (기반 작업, 먼저)

**로스터 스키마** (`/roster/{playerId}`)
```json
{
  "name": "정민", "fullName": "변정민", "aliases": ["변정민"],
  "role": "guest", "positions": ["CM"], "jerseyNo": null, "active": true
}
```
- 별칭 예: 정민 ↔ 변정민, 해근 ↔ 이해근, 재혁 ↔ 장재혁(시트에서 철자가 달라 집계 누락된 케이스). 주의: 주열(정주열)과 용병 박주열은 다른 사람이므로 별칭으로 묶지 않음.
- 포지션 코드 사전 정리: 시트에 쓰인 표기(`RB, GK, CAM, LDM, SW, LS, LWB, WF, WB, MF, DM, CB, LC, 중미, 센백` 등)를 앱 포지션 체계로 정규화하는 매핑 테이블.

**경기 스키마** (`/matches/{matchId}` — 배열이 아니라 ID 키 객체)
```json
{
  "id": "2026-10-17-segok", "date": "2026-10-17", "venue": "세곡체육공원", "opponent": "세리에",
  "quarterCount": 4, "onFieldSize": 11,
  "attendees": ["우성", "형록", ...],
  "quarters": {
    "1Q": { "formation": "4-2-3-1",
            "lineup": { "ST": "우성", "LW": "지호", ... },
            "subs": [ { "in": "재혁", "out": "지용" } ],
            "coords": {} },
    ...
  },
  "events": [ { "quarter": "2Q", "type": "goal", "scorer": "지호", "assister": "진환" } ],
  "status": "final" | "draft"
}
```
- 교체는 시트처럼 `in/out` 쌍 배열로 저장 → 실 참여 0.5 계산을 저장 데이터만으로 재현 가능.
- 쓰기는 `/matches/{id}`, `/roster/{id}` 단위 PUT/PATCH로 바꿔 동시 편집 충돌 제거.
- 경기장 목록을 `/settings/venues`로 이동.

**이관 스크립트** (`tools/import-sheet.py`, 1회성)
- 시트 xlsx 내보내기 → 경기 시트 31개를 파싱(쿼터 보드 격자 → lineup, In/Out 열 → subs, Y/Z열 → 골/어시) → 위 스키마 JSON 생성 → Firebase REST로 업로드.
- 격자 위치 → 포지션 매핑: 행(ST라인/공미라인/중미라인/수비라인/GK) × 열(C~G 좌→우)로 추정하고, 포메이션은 라인별 인원으로 역산(1-3-2-4-1 → 4-2-3-1 등).
- 검증: 이관 후 선수별 총 쿼터·골·어시가 대시보드 C~E열과 일치하는지 자동 비교. 불일치 명단을 출력해 수동 확인.
- 기존 Firebase 3경기는 시트 버전으로 대체(날짜 동일).

### Phase 1 — 쿼터 보장 엔진 (`js/quota.js`)

- 순수 함수 모듈: `computeParticipation(match)` → 선수별 {출전 쿼터, 실 참여, 교체 횟수}, `computeTargets(match)` → 목표 평균, 쿼터별 인원, 과/부족 선수.
- 시트 규칙 그대로: 교체 In/Out 각 0.5 차감, 목표 = Σ(쿼터별 출전 인원)/참석자 수.
- 경기 설정에 **쿼터 수(4/5)·출전 인원(10/11)** 선택 추가.
- 화면: 참석자 표에 `실참여 / 목표` 와 편차를 색으로 표시(예: 2.5 / 3.1 → 부족 → 파랑, 4 / 3.1 → 과다 → 빨강). 배치 중 실시간 갱신.
- Node 테스트 파일로 시트의 실제 경기(예: 10.17 세곡)를 넣어 X열 값과 같은지 검증.

### Phase 2 — 선호 포지션 기반 자동 초안 (`js/autodraft.js`)

입력: 참석자 + 로스터 포지션, 쿼터 수, 쿼터별 포메이션(기본 4-2-3-1), 선택 제약(고정 배치·특정 쿼터 불참·늦게 옴/일찍 감·GK 지정).

알고리즘(결정적, 수 ms 내):
1. **목표 쿼터 배분**: 총 슬롯(인원×쿼터)을 참석자에게 내림/올림으로 나눔. 늦게 오는 선수는 가능한 쿼터만 배분.
2. **쿼터별 출전 선수 선택**: 누적 쿼터가 적은 선수 우선, 연속 휴식 방지, 같은 사람이 매번 1Q만 빠지지 않도록 휴식 쿼터 분산.
3. **포지션 배정**: 선수×슬롯 적합도 행렬(1순위 포지션 3점, 같은 라인·같은 측면 2점, 같은 라인 1점, 그 외 0, GK는 GK 선호자만) → 최대 가중 매칭(헝가리안, 11×11이라 가벼움).
4. **후처리**: 한 선수가 4쿼터 내내 같은 포지션이면 다양성 가점으로 교환 시도, 쿼터 간 변경 최소화.
5. 결과는 초안(draft)으로 적용. 각 선수 카드에 "왜 여기인지"(1순위/2순위/대체) 표시.

UI: "자동 초안 만들기" 버튼 → 결과 적용 → 사용자가 특정 카드를 🔒 잠그고 "다시 생성"하면 잠긴 것만 유지하고 나머지 재계산.

### Phase 3 — 경기 당일 화면 재설계 (모바일 우선)

- 흐름을 단계로: ① 참석 체크 → ② 쿼터·포메이션 설정 + 자동 초안 → ③ 배치 다듬기 → ④ 실시간 기록 → ⑤ 저장. 상단에 고정 요약 바(참석 N명 · 목표 X.X Q · 균형 ✓/⚠).
- 참석 체크: 최근 참석 선수 우선 정렬, 검색, 용병 섹션 접기 → 리스트 길이 절반 이하.
- 피치 카드: 드롭다운 제거, 이름 칩만 표시. 탭하면 하단 시트(벤치 목록, 각자 `실참여/목표` 포함)에서 선택, 데스크톱은 드래그 유지. 교체는 칩 길게 누르기/⇄ 버튼으로 In/Out 지정.
- 벤치를 "이번 쿼터 쉬는 사람" 명확한 영역으로, 각 칩에 누적 쿼터 표시.
- 4개 미니맵 → 쿼터별 라인업 요약 스트립(포메이션 + 11명 이름 + 교체) 로 교체. 이미지 내보내기는 유지.
- 이모지 라벨 정리, 카드 테두리·그림자 완화, 모바일 폰트 크기·터치 영역 확보. 기록 탭 페이드인 제거.

### Phase 4 — 시즌 스탯을 대시보드와 동일하게

- 지표 추가: 총 쿼터(실 참여 합), 평균 쿼터, 참여횟수, 승/무/패·승률, 쿼터별 득·실점.
- 시즌 필터(연도), 선수별 상세(경기별 쿼터/골/어시 타임라인).
- CSV 업로드 제거(이관으로 대체), CSV/xlsx 내보내기는 시트 레이아웃과 호환되게 유지.
- 기록 조회에서 교체 In/Out과 실 참여 표시.

### Phase 5 — 선택 과제

- 보안 규칙: 현재는 익명 인증만 있으면 누구나 쓰기 가능. 최소한 스키마 검증 규칙(`.validate`) 추가, 장기적으로 Cloud Function 경유 쓰기 + 암호 검증.
- 시트로 되돌리기(앱 → 시트 레이아웃 xlsx) 기능으로 팀이 익숙한 형식 백업.

## 4. 확인이 필요한 사항

1. **원본 결정**: 이관 후 시트는 백업으로만 두고 앱이 원본이 되는 방향이 맞는지.
2. **격자 → 포지션 해석**: 시트 보드의 행/열을 포지션으로 자동 추정할 계획인데, 일부 경기는 10명 배치(3-4-2 등)라 역산이 애매할 수 있음 → 이관 결과를 한 번 같이 검수.
3. **포지션 코드 정규화**: `WF`, `WB`, `SW`, `LC`, `중미`, `센백` 같은 표기의 의미 확인.
4. **기술 스택**: 빌드 없이 GitHub Pages에 그대로 올리는 바닐라 JS 구조를 유지하되 ES 모듈로 파일만 분리하는 것을 권장(지금 방식과 배포 동일).

## 5. 권장 순서

Phase 0 → 1 → 2 → 3 → 4. Phase 0·1은 데이터 정합성이라 먼저, Phase 2(자동 초안)는 1의 엔진 위에서 바로 만들 수 있고, 3(디자인)은 2의 UI가 들어갈 자리이므로 함께 진행하는 것이 효율적.
